# แนวทางแก้ไข logic เบิก–ยืมของ CAMMS

วันที่ตรวจแหล่งอ้างอิง: 16 พฤศจิกายน 2569

สถานะ: ข้อเสนอ ยังไม่ได้ดำเนินการแก้โค้ดตามเอกสารนี้

## หลักที่ใช้เลือกแนวทาง

แยกสามเรื่องออกจากกัน: กลไกความถูกต้องของซอฟต์แวร์, แนวปฏิบัติงานคลัง, และข้อกำหนด/อำนาจอนุมัติของหน่วยงาน ไม่เรียกข้อเสนอทุกข้อว่าเป็นมาตรฐานบังคับเดียวกัน

ใช้ฐานข้อมูล PostgreSQL เดิมและธุรกรรมสั้น รักษาสิทธิ์เดิม ไม่เพิ่มระบบ microservices หรือ distributed saga สำหรับงานที่บันทึกจบในฐานข้อมูลเดียวได้ การล็อกต้องมีลำดับเดียวกันทุกเส้นทางและอ่านยอดใหม่หลังได้ล็อก [1][2]

## 1. ป้องกันฟอร์มเก่าเขียนทับสต็อก — ทำก่อน

ข้อเสนอ:

- ฟอร์มแก้ไขชื่อ/ประเภท/หน่วย/สถานที่/หมายเหตุ ไม่ส่งหรืออัปเดต quantity ของรายการที่มีอยู่แล้ว แม้ client ส่ง field นี้มาก็ไม่ใช้เป็นยอดใหม่
- แยกการเปลี่ยนจำนวนเป็นรับเข้า, เบิก, คืน, ปรับยอดตรวจนับ และย้อนรายการ แต่ละรายการมีจำนวน ผู้ทำ เวลา เหตุผล และเอกสารอ้างอิง
- เพิ่ม version สำหรับ optimistic concurrency control ในการแก้ข้อมูลทั่วไป อัปเดตได้เมื่อ version ตรงกับที่เปิดฟอร์ม ถ้าไม่ตรงให้แจ้งโหลดข้อมูลล่าสุด ห้ามทับเงียบ ๆ
- การเพิ่ม–ลดใช้ delta กับยอดล่าสุดใน transaction พร้อมตรวจยอดไม่ติดลบ ไม่ใช้ยอด absolute จากฟอร์มเก่า
- การตรวจนับซึ่งจำเป็นต้องระบุยอด absolute ต้องอ่านยอดใหม่ภายใต้ lock แล้วคำนวณส่วนต่างและบันทึกการปรับยอด หากมีรายการเคลื่อนไหวระหว่างตรวจนับ ต้องตรวจซ้ำหรือเทียบกับเวลาตัดยอด

การล็อกแถวอย่างเดียวไม่แก้ lost update จากฟอร์มที่เปิดค้าง ถ้ายังนำ literal quantity เก่ามาเขียนทับ การแยก field และตรวจ version จึงสำคัญควบคู่กับ locking ข้อนี้เป็นข้อเสนอออกแบบที่ประยุกต์จากพฤติกรรม PostgreSQL [1][2] การใช้เอกสารรับ–จ่าย/ปรับยอดสอดคล้องกับแนวปฏิบัติระบบคลัง [5]

เกณฑ์รับงาน: เปิดฟอร์มตอนเหลือ 10 เบิก 3 แล้วบันทึกแก้ชื่อจากฟอร์มเก่า ต้องยังเหลือ 7; สองคนแก้ metadata เดียวกันต้องเกิดผลสำเร็จหนึ่งฉบับและแจ้ง conflict อีกฉบับ

## 2. ป้องกันการส่งคำขอซ้ำ — ทำก่อน

ใช้ idempotency key หนึ่งค่าต่อการยืนยันตะกร้า สร้างที่ client และใช้ค่าเดิมเมื่อ retry เพราะขาดการตอบกลับ ไม่สร้าง key ใหม่เพียงเพราะเครือข่ายขัดข้อง [3]

ข้อเสนอสำหรับ CAMMS:

- สร้าง request_batches มี request_key, created_by, payload_hash และเชื่อมกับเอกสารทั้งหมดของตะกร้า
- บังคับ UNIQUE(created_by, request_key) ที่ฐานข้อมูล ไม่ใช้แค่การเช็ก SELECT ก่อน INSERT [4]
- canonical payload ต้องรวมรายการที่เรียงตาม ID, จำนวน, เบิก/ยืม, วันคืน, วัตถุประสงค์ และข้อมูลผู้รับที่มีผลต่อรายการ
- key เดิม + payload เดิม: คืน batch และ document IDs เดิม ไม่ตัดสต็อกซ้ำ
- key เดิม + payload ต่าง: ปฏิเสธและแจ้งให้เริ่มคำขอใหม่
- จอง key และสร้างเอกสาร/รายการเคลื่อนไหวใน transaction เดียว หาก rollback ทั้งชุด key ต้องไม่ค้างเป็น success
- คำขอซ้ำพร้อมกันให้รอผลธุรกรรมแรกหรือแจ้งกำลังประมวลผล โดยห้ามสร้างเอกสารชุดที่สอง
- ตรวจสิทธิ์ผู้เรียกทุกครั้งก่อนคืนผลเก่า ไม่ให้ key กลายเป็นช่องอ่านข้อมูลผู้อื่น
- เก็บ batch สำหรับการตรวจสอบย้อนหลัง ไม่คัดลอกอายุ key 24 ชั่วโมงของ Stripe มาเป็นกติกางานพัสดุโดยอัตโนมัติ

Stripe เป็นตัวอย่างการออกแบบ API ไม่ใช่มาตรฐานบังคับของระบบพัสดุ แนวทาง unique key และ parameter matching นำมาประยุกต์ใช้เพื่อให้ retry ปลอดภัย [3][4]

เกณฑ์รับงาน: ส่ง payload เดียวกันพร้อมกัน 2 ครั้งด้วย key เดียว ต้องได้ document IDs ชุดเดียวและมี stock movement หนึ่งชุด; กรณี response หายหลัง commit ต้อง retry แล้วได้ผลเดิม

## 3. คืนครุภัณฑ์ก่อนกำหนด

เสนอให้รับคืนได้ตั้งแต่สถานะ active_borrow หรือ partially_returned โดยไม่ต้องรอ due_date กำหนดคืนใช้สำหรับเตือน/ติดตามการเกินกำหนด ไม่ใช่วันแรกที่อนุญาตให้รับคืน ข้อนี้เป็นข้อเสนอ workflow ไม่ใช่การอ้างว่ามีกฎหมายกำหนดให้ซอฟต์แวร์ทำเช่นนี้

คงการตรวจผู้มีสิทธิ์รับคืน จำนวนค้างคืน สภาพสิ่งของ และหลักฐานการคืน การคืนชำรุดไม่ทำให้พร้อมยืมโดยอัตโนมัติ การสูญหายไม่ควรนำกลับเข้าคลังในสถานะปกติ

ปรับทั้งปุ่มรายชิ้น ปุ่มคืนทั้งหมด และ server validation ให้ตรงกัน ห้ามแก้เฉพาะ UI

เกณฑ์รับงาน: คืนก่อน/ตรง/หลังกำหนดได้ตามสถานะ; คืนซ้ำเกินยอดไม่ได้; ของชำรุดต้องไม่ปรากฏเป็นพร้อมยืม

## 4. ตรวจวันคืนที่เซิร์ฟเวอร์

OWASP แนะนำให้ตรวจทั้งรูปแบบและความหมายของข้อมูล รวมถึงความสัมพันธ์ของวันที่ และไม่พึ่ง validation ฝั่ง client [6]

ข้อเสนอ:

- คำขอใหม่และการแก้วันคืน: ใช้วันปัจจุบันของ Asia/Bangkok เป็นฐาน โดยอนุญาตวันเดียวกันหากหน่วยงานไม่ได้กำหนดเวลาเป็นชั่วโมง
- วันคืนต้องไม่ก่อนวันที่ยืม/วันที่เริ่มใช้งาน; หากปัจจุบันไม่มีวันเริ่มใช้งานแยก ให้ใช้วันที่ส่งคำขอเป็นฐาน
- ตรวจ server ทุก entry point ที่สร้างหรือแก้วันคืน และแสดงข้อความตรงกันกับ UI
- ห้ามนำกฎห้ามย้อนหลังไปปิดกั้นการคืนเอกสารเก่าที่เลยกำหนด
- ถ้าคำขอรออนุมัติจนพ้นวันคืนเดิม ให้แอดมินยืนยัน/กำหนดวันใหม่หรือปฏิเสธอย่างชัดเจน ไม่เปลี่ยนวันเงียบ ๆ

เกณฑ์รับงาน: ส่ง API โดยตรงด้วยวันย้อนหลังถูกปฏิเสธ; ทดสอบช่วงก่อน/หลังเที่ยงคืนกรุงเทพฯ; เอกสารเก่า overdue ยังรับคืนได้

## 5. คำขอค้างอนุมัติหลังตัดสต็อก

CAMMS ปัจจุบันตัดวัสดุทันทีที่ส่งคำขอ ตามการตัดสินใจของผู้ใช้ และคืนยอดเมื่อยกเลิก/ปฏิเสธ การตัดก่อนอนุมัติเป็นนโยบายนี้ ไม่ใช่ข้อบังคับมาตรฐานสากลหรือข้อรับรองความถูกต้องทางบัญชี

แนะนำเริ่มจากแจ้งเตือนตาม SLA ที่หน่วยงานกำหนด ไม่ยกเลิกและคืนยอดตามเวลาตายตัวอัตโนมัติทันที เพราะยังต้องแยกว่ามีการนำของออกไปจริงแล้วหรือไม่ ไม่มีตัวเลข SLA สากลที่ใช้แทนหน่วยงานได้

ควรแยก submitted_at, approved_at, handed_over_at/received_at และเวลาตัดยอดในรายงาน ไม่แสดงยอดตัดรออนุมัติว่าเป็นรายการอนุมัติ/จ่ายจริงแล้ว ต้องตรวจ workflow กับผู้รับผิดชอบพัสดุของหน่วยงานก่อนใช้รายงานทางการ

หากภายหลังเลือก auto-expire ให้มีสถานะ/เหตุผลชัดเจน ล็อกเอกสาร แข่งกับ approval อย่างปลอดภัย และคืนเฉพาะ net debit ที่ยังไม่คืน ห้ามคืนสต็อกโดยตั้งยอดกลับไปเป็นค่าเดิม เพราะอาจทับความเคลื่อนไหวใหม่

## 6. วัสดุใช้ไม่หมดและการคืนบางส่วน

เพิ่มธุรกรรมคืนวัสดุ แยกจากการย้อนทั้งเอกสาร:

- อ้างอิงบรรทัดที่จ่ายแล้ว ระบุจำนวนส่งคืนและจำนวนที่เจ้าหน้าที่รับเข้าจริง
- จำนวนสะสมที่รับคืนต้องไม่เกินจำนวนที่จ่ายจริงหักยอดที่คืน/ย้อนแล้ว
- เพิ่มสต็อกเฉพาะจำนวนที่ตรวจรับและพร้อมใช้งาน; ของเสียหายหรือไม่ผ่านตรวจต้องแยกสถานะ/พื้นที่ ไม่เพิ่มยอดพร้อมเบิก
- เก็บเหตุผล ผู้รับคืน เวลา และประวัติการคืนแต่ละครั้ง ไม่ลบรายการเบิกต้นฉบับ
- ป้องกันการคืนบางส่วนแล้วใช้ย้อนเอกสารเต็มจำนวนซ้ำ

ถ้าวัสดุมีการตีมูลค่า ต้องกำหนดวิธีคิดต้นทุนคืนกับผู้รับผิดชอบบัญชีก่อนเพิ่ม logic มูลค่า ไม่สมมติ FIFO/เฉลี่ยจากจำนวนเพียงอย่างเดียว

## 7. รับเข้าและปรับยอดตรวจนับ

เพิ่มเอกสารรับเข้าและเอกสารปรับยอดพร้อมการอนุมัติตามสิทธิ์เดิม ห้ามแก้ quantity ตรงในฟอร์มทั่วไป ทุก movement ต้องเชื่อมเอกสารและเหตุผล โดยใช้วิธีเพิ่ม–ลดตามยอดล่าสุด ตัวอย่างระบบคลังจาก Microsoft แยก receipt, issue, movement และ counting/adjustment journals [5]

ยอดตั้งต้นก่อนเริ่มมี ledger ต้องมี opening balance ที่อ้างอิงได้ จากนั้นตรวจสมการ:

ยอดปัจจุบัน = ยอดตั้งต้น + ผลรวม movement ที่มีผล

สร้างรายงานเทียบยอดกับ ledger หากไม่ตรงให้แจ้งตรวจสอบ ห้ามแก้ประวัติย้อนหลังเงียบ ๆ การยกเลิกใช้เอกสาร/รายการกลับทางและอ้างอิงต้นฉบับ

## 8. เชื่อมเอกสารจากตะกร้าเดียวกัน

ใช้ request_batches ในข้อ 2 เป็น parent ของเอกสาร material_issue, asset_borrow และ asset_handover ไม่ต้องสร้างกลไกซ้ำอีกชุด

เก็บ batch_id ในเอกสาร แสดงเลขชุดและลิงก์ไปทุกเอกสารลูก สรุปสถานะจากลูก ไม่บังคับให้ลูกทุกประเภทใช้สถานะเดียวกัน

การสร้างชุดยังต้อง atomic แต่การอนุมัติภายหลังแต่ละลูกอาจต่างเวลา จึงเสนอให้อนุมัติ/ยกเลิกรายเอกสารก่อน หากจะทำปุ่มทั้งชุด ต้องตรวจสิทธิ์และสถานะทุกใบใน transaction เดียว ไม่ยกเลิกใบที่จ่าย/รับคืนไปแล้วอัตโนมัติ

## ลำดับดำเนินการ

1. ปิดช่องการเขียนทับ quantity และทำ stock adjustment แยก; เพิ่ม request_batches + idempotency
2. เปิดรับคืนก่อนกำหนดและตรวจวันที่ฝั่ง server
3. เพิ่ม stock receipt / partial material return และ reconciliation
4. เพิ่มการติดตามคำขอค้างและข้อมูลส่งมอบจริง โดยกำหนด SLA กับหน่วยงานก่อนเปิด auto-expiry

การตรวจข้ามขั้นสำคัญ: submit retry, submit พร้อมกัน, approval แข่ง cancellation, return แข่ง reversal, ฟอร์มเก่าแข่งการเบิก, restore ข้อมูลเก่า และ mixed-cart ลูกใบที่สองล้มเหลว ต้องไม่ทิ้ง stock movement บางส่วน
