# CAMMS: ส่งต่องานแก้ Business Logic เบิก–ยืม–อนุมัติ

วันที่: 2026-11-15

## บทบาทและขอบเขต

ผู้ใช้ให้ agent ผู้จัดทำรายงานเป็นผู้วิเคราะห์และตรวจงาน ส่วน agent ผู้รับงานเป็นผู้ลงมือแก้ไข ผู้ใช้ต้องการประหยัด usage: ทำเฉพาะรายการในรายงาน ไม่ขยายเป็น audit ทั้งระบบ

รายงานนี้มาจากการอ่านโค้ด ยังไม่ได้จำลองปัญหากับฐานข้อมูล และยังไม่ได้แก้ข้อค้นพบด้านล่าง ให้ผู้รับงานตรวจยืนยันกับโค้ดปัจจุบันก่อนแก้ เพราะ working tree มีงานอื่นค้างอยู่

อ่าน `AGENTS.md`, `docs/context/PRODUCT.md`, `docs/context/README.md`, `docs/context/AGENTS.md` ตามข้อกำหนดของ repo และใช้ skill ที่เกี่ยวข้อง ห้าม reset, stash หรือทับงานเดิมของผู้ใช้

## 1. คำขอที่ไม่อนุมัติถูกซ่อนจากรายการของผู้ขอ

**ความสำคัญ: สูง — กระทบการติดตามผลคำขอ**

หลักฐาน:

- `features/disbursements/postgres-queries.ts` ใน `getPostgresDisbursements()` ประมาณบรรทัด 27–31: เมื่อไม่ได้ใช้ `historyOnly` หรือ `hideCompleted` จะเพิ่มเงื่อนไข `d.status <> 'rejected'` เสมอ
- `app/(dashboard)/disbursements/page.tsx` ส่ง query สำหรับหน้ารายการของผู้ใช้ผ่านเส้นทางนี้ และผู้ใช้ทั่วไปไม่ได้ใช้ history สำหรับ admin
- `features/disbursements/postgres-actions.ts` ใน `rejectPostgresDisbursement()` เปลี่ยนสถานะเป็น `rejected` และเก็บเหตุผลใน `reversal_reason`

ผลที่คาดจากโค้ด: เมื่อ admin ไม่อนุมัติ คำขอจะหายจากรายการของผู้ขอ แทนที่จะให้ติดตามผลได้ แม้กรอง `status=rejected` ก็จะชนกับเงื่อนไขตัด rejected หากใช้โหมดปกติ

สิ่งที่ต้องทำ:

1. ยืนยันเส้นทาง “รายการของฉัน” และสิทธิ์อ่านข้อมูลเดิม
2. ปรับ query ให้ผู้ขอติดตามรายการที่ไม่อนุมัติของตนเองได้ โดยไม่เปลี่ยน RBAC/RLS และไม่ทำให้รายการที่จบแล้วกลับเข้าคิวอนุมัติ
3. ตรวจว่าหน้ารายละเอียดแสดงเหตุผลปฏิเสธที่บันทึกไว้ได้ ใช้ UI เดิมเท่าที่ทำได้

เกณฑ์รับงาน: รายการของผู้ขอแสดงคำขอ rejected ที่มีสิทธิ์อ่าน, กรอง rejected ได้, คิวอนุมัติยังไม่รวมรายการที่จบแล้ว และไม่มีข้อมูลของผู้ใช้อื่นรั่วไหล

## 2. Audit log ระบุสถานะก่อนอนุมัติผิด

**ความสำคัญ: กลาง — ประวัติการเปลี่ยนแปลงไม่ตรงเหตุการณ์จริง**

หลักฐาน:

- `features/disbursements/postgres-actions.ts` ใน `confirmPostgresDisbursement()` ประมาณบรรทัด 242 อนุญาตทั้ง `draft` และ `pending_approval`
- ตอนเขียน `CONFIRM_DISBURSEMENT` ประมาณบรรทัด 361 ใช้ `JSON.stringify({ status: 'draft' })` เป็น `old_data` เสมอ

สิ่งที่ต้องทำ: ใช้สถานะจริงจากเอกสารที่อ่านและล็อกไว้ (`doc.status`) แทนค่าคงที่ โดยคง transaction และการล็อกเดิม

เกณฑ์รับงาน:

- อนุมัติคำขอ pending: `old_data.status` เป็น `pending_approval`
- ยืนยันเอกสาร draft: `old_data.status` เป็น `draft`
- `new_data.status` ยังตรงกับประเภทเอกสาร เช่น `active_borrow` หรือ `confirmed`
- ไม่ย้อนแก้ audit log เก่า และไม่ปรับข้อมูลฐานข้อมูลจริงโดยตรง

## 3. รับคืนก่อนกำหนดไม่ได้ — ประเด็นรอยืนยันนโยบาย

**ยังไม่สรุปว่าเป็น bug และยังไม่ให้แก้โดยอาศัยการคาดเดา**

หลักฐาน:

- `returnPostgresDisbursementItem()` ใน `features/disbursements/postgres-actions.ts` ประมาณบรรทัด 395–398 ตรวจ `due_date <= วันนี้ใน Asia/Bangkok` มิฉะนั้นแจ้ง “ยังไม่ถึงกำหนดคืนพัสดุ”
- ช่องทางคืนทั้งเอกสารตรวจแบบเดียวกัน ประมาณบรรทัด 512–515
- UI มีเงื่อนไขวันที่ด้วย ให้ตรวจ `transaction-items-table.tsx`, `grouped-transactions-table.tsx` และปุ่มคืนที่เกี่ยวข้องหากได้รับอนุญาตให้เปลี่ยนกติกา

สิ่งที่ต้องทำตอนนี้: ตรวจเอกสารหรือข้อกำหนดเดิมว่าการห้ามคืนก่อนกำหนดเป็นความตั้งใจหรือไม่ หากไม่มีข้อสรุป ให้รายงานกลับผู้วิเคราะห์และทำข้อ 1–2 ต่อ ไม่หยุดงานทั้งหมด และไม่เปลี่ยนกติกาข้อนี้เอง

## บริบทงานก่อนหน้า: รูปแบบ Logs ที่ผู้ใช้ยืนยันแล้ว

“ประวัติการอนุมัติ” ต้องเป็นตัวเลือกใน dropdown “การทำรายการ” ของหน้า Logs และใช้ **ตาราง audit logs เดียวกับ Logs อื่น** กดแถวเพื่อเปิดข้อมูลก่อน–หลัง ห้ามนำตารางเอกสารเบิก–ยืมมาแสดงแทนอีก

- ตัวเลือกใช้ `action=approval_history` และสีม่วง
- `features/admin/audit-action-filter.ts` รวม action ที่มีอยู่ใน audit log
- `app/(dashboard)/admin/audit-logs/page.tsx` ใช้ `AuditLogsClient`
- หน้า Logs ไม่มีปุ่ม “ล้างตัวกรอง” ตามความต้องการผู้ใช้

คงพฤติกรรมที่ผู้ใช้ยืนยันนี้ไว้ ไม่ต้องออกแบบ UI ใหม่

## แนวทางลงมือและตรวจสอบ

1. ดู `git status`/diff ก่อนเริ่ม แยกงานของตนออกจากงานค้าง ใช้ branch งานเดิมที่เหมาะสมหรือสร้าง branch ตาม workflow โดยไม่ล้าง working tree
2. ยืนยันสาเหตุและเพิ่ม regression test ที่ทดสอบพฤติกรรมจริงสำหรับข้อ 1–2 ก่อนแก้ หลีกเลี่ยง test ที่เช็กเพียงข้อความ source code
3. ใช้ fixture หรือ mock ตามรูปแบบ tests เดิม ห้ามทดลอง mutation กับ production หรือ apply migration โดยไม่ได้รับอนุญาต
4. รัน focused tests ก่อน แล้วตรวจ typecheck/lint ตามไฟล์ที่เปลี่ยน ปฏิบัติตาม gate ที่ repo/skill กำหนด ไม่รันชุดหนักซ้ำโดยไม่มีเหตุ
5. ไม่มีความจำเป็นต้องเปลี่ยน schema, migration, permissions, สูตรค่าเสื่อม หรือ dependency สำหรับสองข้อแรก หากพบว่าจำเป็น ให้รายงานเหตุผลก่อนขยายงาน
6. ส่งกลับ: ไฟล์ที่แก้, พฤติกรรมก่อน–หลัง, คำสั่งตรวจพร้อมผลจริง, สิ่งที่ยังไม่ได้ตรวจ และข้อสงสัยเรื่องนโยบายคืนก่อนกำหนด ไม่อ้างว่าทดสอบฐานข้อมูลหรือ browser แล้วหากยังไม่ได้ทำ

ให้ผู้วิเคราะห์ตรวจ diff และผลทดสอบก่อนสรุปงาน ไม่ commit/push/deploy เว้นแต่ผู้ใช้อนุญาตเพิ่มเติม
